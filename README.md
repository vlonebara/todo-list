# Планировщик задач Todo List

Todo List — веб-приложение для планирования личных задач. Оно позволяет хранить задачи с датой, заголовком, комментарием и правилом повторения, искать их и отмечать выполненными.

Если у задачи есть правило повторения, после выполнения сервер рассчитывает следующую дату. Одноразовая задача после выполнения удаляется. Приложение включает веб-интерфейс в каталоге `web` и HTTP API на Go.

Все задачи из ТЗ были реализованы в проекте. О них ниже.

## Возможности

- создание, просмотр, редактирование и удаление задач;
- список до 15 ближайших задач, отсортированных по дате;
- поиск по заголовку и комментарию, а также выбор задач на конкретную дату;
- перенос повторяющихся задач на следующее выполнение;
- необязательная аутентификация по паролю и JWT;
- раздача веб-интерфейса и его статических файлов.

## Настройка окружения

При запуске из корня проекта приложение один раз загружает конфигурацию из окружения и `.env`, если файл существует. Переменные, уже заданные в окружении процесса, имеют приоритет. Готовые настройки передаются серверу, БД и сервису аутентификации. Для применения новых значений нужен перезапуск сервера. Файл `.env` исключён из Git и Docker build context.

Пример `.env`:

```dotenv
TODO_PORT=7540
TODO_DBFILE=./scheduler.db
TODO_PASSWORD=change-this-password
# Необязательно: постоянный ключ JWT для сохранения токенов после перезапуска.
# TODO_JWT_SECRET=replace-with-a-random-secret-at-least-32-bytes-long
```

Описание переменных:

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `TODO_PORT` | Порт HTTP-сервера | `7540` |
| `TODO_DBFILE` | Путь к файлу SQLite | `scheduler.db` |
| `TODO_PASSWORD` | Пароль для входа. Если пустой, API работает без проверки токена | пусто |
| `TODO_JWT_SECRET` | Необязательный ключ для подписи и проверки JWT; если задан, нужно не менее 32 байт | случайный ключ на время работы сервера |

Для аутентификации достаточно задать `TODO_PASSWORD`. Если `TODO_JWT_SECRET` отсутствует или пустой, сервер один раз создаёт случайный ключ. После перезапуска сервера с автоматическим ключом нужно войти заново.

Чтобы токены оставались действительными после перезапуска, задайте постоянный `TODO_JWT_SECRET` длиной не менее 32 байт. Секрет можно сгенерировать командой `openssl rand -base64 32`. Не используйте примерные значения пароля и секрета в реальной установке.

`TODO_DBFILE` может быть относительным или абсолютным путём. Относительный путь считается от текущего рабочего каталога процесса. Каталог для файла должен существовать и быть доступен для записи.

## Локальный запуск

В корне проекта загрузите зависимости и запустите приложение:

```bash
go mod download
go run ./cmd
```

При первом запуске сервер создаст SQLite-файл и таблицу `scheduler`. Если переменные не заданы, сервер будет слушать порт `7540`, а база появится в `scheduler.db` в текущем каталоге. Веб-интерфейс будет доступен по адресу [http://localhost:7540](http://localhost:7540).

Остановить сервер можно сочетанием `Ctrl+C`; сервер завершит обработку активных запросов и корректно остановится.

## Тесты

Тесты в каталоге `tests` — интеграционные: они отправляют HTTP-запросы работающему серверу и читают ту же базу SQLite. Запустите сервер и тесты в двух терминалах из корня проекта. Для тестов используется отдельная база, чтобы не менять обычные данные.

Терминал 1 — сервер:

```bash
TODO_PASSWORD= TODO_PORT=7540 TODO_DBFILE="$(pwd)/test-scheduler.db" go run ./cmd
```

Терминал 2 — полный набор тестов:

```bash
TODO_PASSWORD= TODO_PORT=7540 TODO_DBFILE="$(pwd)/test-scheduler.db" go test ./...
```

Пустое значение `TODO_PASSWORD` отключает проверку авторизации для тестового запуска: в настройках тестов токен не задан. Сервер и тесты должны использовать одинаковые `TODO_PORT` и `TODO_DBFILE`. Переменная `TODO_DBFILE` в командах выше получает абсолютный путь, поэтому корректно работает и при запуске Go-тестов из каталога пакета.

Чтобы запустить только тест раздачи веб-файлов:

```bash
TODO_PASSWORD= TODO_PORT=7540 TODO_DBFILE="$(pwd)/test-scheduler.db" go test -run '^TestApp$' ./tests
```

## Запуск через Docker

Соберите образ из корня проекта:

```bash
docker build -t todo-list:local .
```

Запустите контейнер с сохранением базы на хосте:

```bash
mkdir -p data

docker run -d --name todo-list \
  -p 7540:7540 \
  -v "$(pwd)/data:/data" \
  -e TODO_DBFILE=/data/scheduler.db \
  todo-list:local
```

Откройте [http://localhost:7540](http://localhost:7540). Для включения аутентификации добавьте к `docker run` параметр `-e TODO_PASSWORD=...`. Постоянный ключ JWT можно передать через `-e TODO_JWT_SECRET=...`; если он задан, нужно не менее 32 байт. Переменные передаются контейнеру при запуске, `.env` внутрь образа не копируется.

Посмотреть логи и остановить контейнер:

```bash
docker logs -f todo-list
docker stop todo-list
```

В Docker-образ входят Linux-бинарник приложения и каталог `web`. Параметр `-p 7540:7540` публикует порт сервера на компьютере. Привязка `data` сохраняет базу при пересоздании контейнера.

## Архитектура проекта

```text
cmd/main.go          загрузка конфигурации и запуск сервера
pkg/config           однократная загрузка настроек из окружения и .env
pkg/server           общий пул БД, HTTP-сервер, статические файлы и остановка
pkg/api              маршруты, HTTP-обработчики, JSON и middleware авторизации
pkg/service          бизнес-логика задач, повторений, поиска и аутентификации
pkg/db               схема SQLite, пул соединений и хранилище задач
web                  HTML, CSS и JavaScript веб-интерфейса
tests                интеграционные тесты HTTP API и работы с БД
```

Обработчик API разбирает HTTP-запрос и передаёт работу сервису. Сервис проверяет данные и обращается к `TaskStore` из пакета `db`. Хранилище выполняет SQL-запросы через общий пул `*sql.DB`, созданный один раз при запуске сервера. Для SQLite пул ограничен одним переиспользуемым соединением. При получении `SIGINT` или `SIGTERM` сервер завершает активные HTTP-запросы и затем закрывает пул БД.

## Краткая документация API

Все даты задач передаются и возвращаются строками в формате `YYYYMMDD` (`20060102`). Ошибки большинства API-методов возвращаются в JSON:

```json
{"error":"task not found"}
```

Если `TODO_PASSWORD` не пустой, запросы к задачам требуют JWT в cookie с именем `token`. Для получения токена отправьте пароль в `/api/signin`; клиент должен сохранить ответный токен в эту cookie. Токен действует 8 часов. При пустом `TODO_PASSWORD` middleware пропускает запросы без токена.

### Маршруты

| Метод и путь | Параметры | Результат |
| --- | --- | --- |
| `POST /api/signin` | JSON `{"password":"..."}` | JSON с полем `token` или `error` |
| `GET /api/nextdate` | `date`, `repeat`; необязательный `now` | Следующая дата обычным текстом или текст ошибки |
| `POST /api/task` | JSON с `date`, `title`, `comment`, `repeat` | JSON с ID созданной задачи |
| `GET /api/task?id=<id>` | ID в query-параметре | Поля задачи: `id`, `date`, `title`, `comment`, `repeat` |
| `PUT /api/task` | JSON с `id`, `date`, `title`, `comment`, `repeat` | Пустой JSON `{}` |
| `DELETE /api/task?id=<id>` | ID в query-параметре | Пустой JSON `{}` |
| `GET /api/tasks` | Необязательный `search` | JSON со списком `tasks` (до 15 задач) |
| `POST /api/task/done?id=<id>` | ID в query-параметре | Пустой JSON `{}`; повторяющаяся задача переносится, одноразовая удаляется |

Неподдерживаемый HTTP-метод получает код `405` и заголовок `Allow` со списком разрешённых методов. Для `PUT /api/task` ошибки входных данных возвращаются с кодом `400`, отсутствие задачи — `404`, сбой БД — `500`. Сообщения ошибок API написаны на английском и начинаются с маленькой буквы.

Поля `title`, `comment` и `repeat` передаются строками. Заголовок обязателен. Если `date` при создании или редактировании пустая, используется текущая дата. Просроченная дата одноразовой задачи заменяется текущей, а для повторяющейся задачи рассчитывается ближайшее выполнение.

Параметр `search` у `GET /api/tasks` ищет подстроку в заголовке и комментарии. Если он соответствует дате `DD.MM.YYYY`, возвращаются задачи на эту дату. Результаты сортируются по дате по возрастанию; максимальное количество записей — 15.

### Правила повторения

Правило хранится в строковом поле `repeat`:

- пустая строка — одноразовая задача;
- `d N` — повтор через `N` дней, от 1 до 400;
- `y` — повтор ежегодно;
- `w N,...` — повтор в указанные дни недели, где 1 — понедельник, 7 — воскресенье;
- `m N,... [M,...]` — повтор в указанные дни месяца; допустимы дни от 1 до 31, `-1` (последний день) и `-2` (предпоследний день). Необязательный список `M` ограничивает месяцы значениями от 1 до 12.

Примеры: `d 7`, `w 1,4,5`, `m -1`, `m 1,15 2,8`.

`GET /api/nextdate` использует те же правила. Параметр `date` содержит исходную дату `YYYYMMDD`, параметр `repeat` — правило, а необязательный `now` — дату отсчёта `YYYYMMDD`. Если `now` отсутствует, используется текущая дата.

## База данных

SQLite хранится в одном файле. При первом запуске создаётся таблица `scheduler`:

| Поле | Назначение |
| --- | --- |
| `id` | Автоинкрементный ID задачи |
| `date` | Дата задачи в формате `YYYYMMDD` |
| `title` | Заголовок |
| `comment` | Комментарий |
| `repeat` | Правило повторения, не более 128 символов |

Для сортировки задач по дате создаётся индекс `idx_scheduler_date`.
