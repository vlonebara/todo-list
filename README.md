# Планировщик задач Todo List

Todo List — веб-приложение для планирования личных задач. Оно позволяет хранить задачи с датой, заголовком, комментарием и правилом повторения, искать их и отмечать выполненными.

Если у задачи есть правило повторения, после выполнения сервер рассчитывает следующую дату. Одноразовая задача после выполнения удаляется. Приложение включает веб-интерфейс в каталоге `web` и HTTP API на Go.

Бэкенд разделён на HTTP-обработчики, сервисы с бизнес-логикой и хранилище SQLite. Общие модели задач используются всеми слоями, а конкретные зависимости собираются при запуске приложения.

## Возможности

- создание, просмотр, редактирование и удаление задач;
- список до 15 ближайших задач, отсортированных по дате;
- поиск по заголовку и комментарию, а также выбор задач на конкретную дату;
- перенос повторяющихся задач на следующее выполнение;
- необязательная аутентификация по паролю и JWT;
- раздача веб-интерфейса и его статических файлов.

## Настройка окружения

При запуске из корня проекта приложение один раз загружает конфигурацию из окружения и `.env`, если файл существует. Переменные, уже заданные в окружении процесса, имеют приоритет. Готовые настройки передаются серверу, БД и сервису аутентификации. Для применения новых значений нужен перезапуск сервера. Файл `.env` исключён из Git и Docker build context.

Пример `.env`:

```dotenv
TODO_PORT=7540
TODO_DBFILE=./scheduler.db
TODO_PASSWORD=change-this-password
# Необязательно: постоянный ключ JWT для сохранения токенов после перезапуска.
# TODO_JWT_SECRET=replace-with-a-random-secret-at-least-32-bytes-long
```

Описание переменных:

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `TODO_PORT` | Порт HTTP-сервера | `7540` |
| `TODO_DBFILE` | Путь к файлу SQLite | `scheduler.db` |
| `TODO_PASSWORD` | Пароль для входа. Если пустой, API работает без проверки токена | пусто |
| `TODO_JWT_SECRET` | Необязательный ключ для подписи и проверки JWT; если задан, нужно не менее 32 байт | случайный ключ на время работы сервера |

Для аутентификации достаточно задать `TODO_PASSWORD`. Если `TODO_JWT_SECRET` отсутствует или пустой, сервер один раз создаёт случайный ключ. После перезапуска сервера с автоматическим ключом нужно войти заново.

Чтобы неистёкшие токены оставались действительными после перезапуска, используйте неизменные `TODO_PASSWORD` и `TODO_JWT_SECRET`. Постоянный ключ должен содержать не менее 32 байт. Секрет можно сгенерировать командой `openssl rand -base64 32`. Не используйте примерные значения пароля и секрета в реальной установке.

`TODO_DBFILE` может быть относительным или абсолютным путём. Относительный путь считается от текущего рабочего каталога процесса. Каталог для файла должен существовать и быть доступен для записи.

## Локальный запуск

В корне проекта загрузите зависимости и запустите приложение:

```bash
go mod download
go run ./cmd
```

При запуске приложение открывает файл SQLite, проверяет соединение и создаёт таблицу `scheduler` с индексом, если их ещё нет. Если переменные не заданы, сервер слушает порт `7540`, база находится в `scheduler.db`, а API работает без аутентификации.

Веб-интерфейс доступен по адресу [http://localhost:7540](http://localhost:7540). Сервер раздаёт файлы из `./web`, поэтому рабочим каталогом должен быть корень проекта.

Остановить сервер можно сочетанием `Ctrl+C`. При `SIGINT` или `SIGTERM` он ждёт завершения активных HTTP-запросов до 5 секунд, затем приложение закрывает пул соединений БД.

## Тесты

Тесты в [tests](./tests) — интеграционные: они отправляют HTTP-запросы работающему серверу и читают ту же базу SQLite. Тесты создают, изменяют и удаляют записи. Команды ниже используют отдельный файл `test-scheduler.db`.

Откройте два терминала в корне проекта. Порт `7540` должен быть свободен; при необходимости задайте другой одинаковый `TODO_PORT` в обеих командах.

Терминал 1 — сервер:

```bash
TODO_PASSWORD= TODO_PORT=7540 TODO_DBFILE="$(pwd)/test-scheduler.db" go run ./cmd
```

Терминал 2 — запуск тестов:

```bash
TODO_PORT=7540 TODO_DBFILE="$(pwd)/test-scheduler.db" go test ./tests -v
```

Пустое значение `TODO_PASSWORD` в команде запуска сервера отключает проверку авторизации и имеет приоритет над значением из `.env`. В таком режиме тестам не требуется актуальный JWT.

Сервер и тесты должны использовать одинаковые `TODO_PORT` и `TODO_DBFILE`. Абсолютный путь к БД позволяет им обращаться к одному файлу, хотя Go запускает тесты из каталога пакета. Сами тесты не загружают `.env`.

В [tests/settings.go](./tests/settings.go) находятся настройки `Port`, `DBFile`, `FullNextDate`, `Search` и `Token`. При проверке сервера с включённой аутентификацией `Token` должен содержать актуальный JWT этого сервера. После истечения токена, смены пароля или перезапуска сервера с автоматическим ключом потребуется получить новый токен.

Для запуска без кеша добавьте `-count=1`:

```bash
TODO_PORT=7540 TODO_DBFILE="$(pwd)/test-scheduler.db" go test ./tests -v -count=1
```

Чтобы запустить только тест раздачи веб-файлов:

```bash
TODO_PORT=7540 TODO_DBFILE="$(pwd)/test-scheduler.db" go test ./tests -v -run '^TestApp$'
```

## Запуск через Docker

Соберите образ из корня проекта:

```bash
docker build -t todo-list:local .
```

Создайте каталог для сохранения базы на хосте:

```bash
mkdir -p data
```

Запуск без аутентификации:

```bash
docker run -d --name todo-list \
  -p 7540:7540 \
  -v "$(pwd)/data:/data" \
  -e TODO_DBFILE=/data/scheduler.db \
  todo-list:local
```

Другой вариант — запуск с настройками из подготовленного `.env`:

```bash
docker run -d --name todo-list \
  --env-file .env \
  -p 7540:7540 \
  -v "$(pwd)/data:/data" \
  -e TODO_PORT=7540 \
  -e TODO_DBFILE=/data/scheduler.db \
  todo-list:local
```

Выберите один вариант запуска. Во втором аутентификация включается значением `TODO_PASSWORD` из `.env`. Явные `TODO_PORT` и `TODO_DBFILE` задают порт и путь к БД внутри контейнера. По умолчанию Dockerfile использует `/app/scheduler.db`; в примерах путь переопределён на `/data/scheduler.db`, чтобы база сохранялась в каталоге `data` на хосте.

Откройте [http://localhost:7540](http://localhost:7540). Переменные передаются контейнеру при запуске; сам файл `.env` в образ не копируется.

Посмотреть логи:

```bash
docker logs -f todo-list
```

`Ctrl+C` завершает просмотр логов. Остановить и затем снова запустить существующий контейнер можно командами:

```bash
docker stop todo-list
docker start todo-list
```

Сборка состоит из двух этапов: образ Go компилирует Linux-бинарник с `CGO_ENABLED=0`, затем бинарник и каталог `web` копируются в Alpine. Параметр `-p 7540:7540` публикует порт сервера на компьютере. Привязка `data` сохраняет базу при пересоздании контейнера.

Обработчики работают с сервисами через интерфейсы из [handler.go](./pkg/handlers/handler.go): разбирают HTTP-запросы и формируют ответы. Сервис проверяет данные и использует интерфейс [TaskStore](./pkg/service/task_service.go). Пакет `db` реализует этот интерфейс и выполняет SQL-запросы. Общие данные передаются через независимые модели из `model`; разбор поисковой даты и правила повторения находятся в сервисах.

Конкретное хранилище, сервисы и HTTP-обработчик создаются в `cmd/main.go`. Здесь выбирается реализация хранилища и управляется временем жизни общего пула `*sql.DB`. Пул открывается один раз при запуске и ограничен одним переиспользуемым соединением. После остановки HTTP-сервера приложение закрывает БД.

## Краткая документация API

Базовый адрес при стандартном порте — `http://localhost:7540`. Тело запросов передаётся с `Content-Type: application/json`. Все поля задачи, включая `id`, возвращаются строками. Даты задач используют формат `YYYYMMDD` (`20060102`). Успешные операции API возвращают код `200`.

Ошибки большинства API-методов возвращаются в JSON:

```json
{"error":"task not found"}
```

### Аутентификация

Если `TODO_PASSWORD` не пустой, запросы к задачам требуют JWT в cookie с именем `token`. Для получения токена отправьте пароль:

```bash
curl --request POST http://localhost:7540/api/signin \
  --header 'Content-Type: application/json' \
  --data '{"password":"change-this-password"}'
```

Успешный ответ имеет вид `{"token":"<jwt>"}`. Подставьте полученный токен вместо `<jwt>` в следующем запросе:

```bash
curl --cookie 'token=<jwt>' http://localhost:7540/api/tasks
```

Сервер возвращает токен в JSON; клиент передаёт его в cookie. JWT подписывается алгоритмом HS256 и выдаётся на 8 часов. Проверяются подпись, срок действия и метка текущего пароля. При отсутствующем, повреждённом или истёкшем токене защищённый API отвечает `401`. При пустом `TODO_PASSWORD` проверка cookie отключена.

`POST /api/signin` и `GET /api/nextdate` доступны без токена. Все методы `/api/task`, а также `/api/tasks` и `/api/task/done` защищены, когда настроен пароль.

### Маршруты

| Метод и путь | Параметры | Результат |
| --- | --- | --- |
| `POST /api/signin` | JSON `{"password":"..."}` | JSON с полем `token` или `error` |
| `GET /api/nextdate` | `date`, `repeat`; необязательный `now` | Следующая дата обычным текстом или текст ошибки |
| `POST /api/task` | JSON с `date`, `title`, `comment`, `repeat` | JSON с ID созданной задачи |
| `GET /api/task?id=<id>` | ID в query-параметре | Поля задачи: `id`, `date`, `title`, `comment`, `repeat` |
| `PUT /api/task` | JSON с `id`, `date`, `title`, `comment`, `repeat` | Пустой JSON `{}` |
| `DELETE /api/task?id=<id>` | ID в query-параметре | Пустой JSON `{}` |
| `GET /api/tasks` | Необязательный `search` | JSON со списком `tasks` (до 15 задач) |
| `POST /api/task/done?id=<id>` | ID в query-параметре | Пустой JSON `{}`; повторяющаяся задача переносится, одноразовая удаляется |

Неподдерживаемый HTTP-метод получает код `405` и заголовок `Allow` со списком разрешённых методов. Для `PUT /api/task` ошибки входных данных возвращаются с кодом `400`, отсутствие задачи — `404`, сбой БД — `500`. Сообщения ошибок API написаны на английском и начинаются с маленькой буквы.

Основные ошибки текущих обработчиков:

| Запрос | Коды ошибок |
| --- | --- |
| `POST /api/signin` | `400` — некорректный JSON; `401` — неверный или ненастроенный пароль |
| `GET /api/nextdate` | `400` — некорректные параметры; ошибка возвращается обычным текстом |
| `POST /api/task`, `GET /api/task`, `DELETE /api/task`, `POST /api/task/done` | `400` — ошибка обработки задачи |
| `PUT /api/task` | `400` — неверные данные; `404` — задача отсутствует; `500` — ошибка БД |
| `GET /api/tasks` | `500` — ошибка получения списка |

Для защищённых маршрутов также возможен `401`, для неподдерживаемых методов — `405`.

### Формат задачи

Пример тела `POST /api/task`:

```json
{
  "date": "20300115",
  "title": "Подвести итог",
  "comment": "Подготовить отчёт",
  "repeat": "d 7"
}
```

Ответ содержит только ID созданной записи: `{"id":"1"}`. При `PUT /api/task` к тем же полям добавляется строковое поле `id`. `GET /api/task` возвращает все пять полей задачи, а `GET /api/tasks` — объект `{"tasks":[...]}`. Пустой список возвращается как `{"tasks":[]}`.

Поля `title`, `comment` и `repeat` передаются строками. Заголовок обязателен. Если `date` при создании или редактировании пустая, используется текущая дата. Просроченная дата одноразовой задачи заменяется текущей, а для повторяющейся задачи рассчитывается ближайшее выполнение.

Параметр `search` у `GET /api/tasks` ищет подстроку в заголовке и комментарии. Если он соответствует корректной дате `DD.MM.YYYY`, возвращаются задачи на эту дату. Результаты сортируются по дате по возрастанию, а при одинаковой дате — по ID. Максимальное количество записей — 15.

Пример поиска с кодированием параметра:

```bash
curl --get http://localhost:7540/api/tasks \
  --cookie 'token=<jwt>' \
  --data-urlencode 'search=08.02.2024'
```

### Правила повторения

Правило хранится в строковом поле `repeat`:

- пустая строка — одноразовая задача;
- `d N` — повтор через `N` дней, от 1 до 400;
- `y` — повтор ежегодно;
- `w N,...` — повтор в указанные дни недели, где 1 — понедельник, 7 — воскресенье;
- `m N,... [M,...]` — повтор в указанные дни месяца; допустимы дни от 1 до 31, `-1` (последний день) и `-2` (предпоследний день). Необязательный список `M` ограничивает месяцы значениями от 1 до 12.

Примеры: `d 7`, `w 1,4,5`, `m -1`, `m 1,15 2,8`.

`GET /api/nextdate` принимает исходную дату `date` в формате `YYYYMMDD`, непустое правило `repeat` и необязательную дату отсчёта `now` в том же формате. Если `now` отсутствует, используется текущая дата. Ответ — следующая дата строго позже `now` обычным текстом.

```bash
curl --get http://localhost:7540/api/nextdate \
  --data-urlencode 'now=20240126' \
  --data-urlencode 'date=20240126' \
  --data-urlencode 'repeat=y'
```

Для этого примера ответ — `20250126`.

## База данных

SQLite хранится в одном файле. При запуске проверяется соединение и выполняется создание таблицы и индекса через `IF NOT EXISTS`:

| Поле | Тип в SQLite | Назначение |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Автоинкрементный ID задачи |
| `date` | `CHAR(8)` | Дата задачи в формате `YYYYMMDD` |
| `title` | `TEXT` | Заголовок |
| `comment` | `TEXT` | Комментарий |
| `repeat` | `VARCHAR(128)` с ограничением длины | Правило повторения, не более 128 символов |

Для сортировки задач по дате создаётся индекс `idx_scheduler_date`.
